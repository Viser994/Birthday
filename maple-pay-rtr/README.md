# Maple Pay RTR API

Simple REST API for Payments Canada Real-Time Rail (RTR) payments.

You do **not** send ISO 20022, UETR, JWS signatures, or member IDs. Those are generated by the API from the Maple Pay RTR data dictionary.

This sandbox is contract-derived. Validate it against the applicable Payments Canada RTR / MyStandards release before production.

## Run locally

```bash
cd maple-pay-rtr
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8080
```

Open:

- Interactive tester: http://localhost:8080
- Swagger docs: http://localhost:8080/docs

## Headers

Only one header is required:

```http
X-API-Key: maple_sandbox_dev_key
```

This also works:

```http
Authorization: Bearer maple_sandbox_dev_key
```

Optional:

```http
Idempotency-Key: order-123
```

Use the same idempotency key if you retry a create. You will get the same payment back instead of a duplicate.

Do **not** send `x-uetr`, `traceability-id`, or `x-jws-signature`. The API adds those when it talks to RTR.

## Send a payment

`POST /v1/payments`

```json
{
  "amount": "25.00",
  "payer": { "name": "Jane Doe", "account": "WALLET-1001" },
  "payee": { "name": "Acme Store", "account": "WALLET-2002" },
  "reference": "INV-1001"
}
```

`currency` defaults to `CAD`. `reference` is optional.

```bash
curl -sS http://localhost:8080/v1/payments \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: maple_sandbox_dev_key' \
  -d '{"amount":"25.00","payer":{"name":"Jane Doe","account":"WALLET-1001"},"payee":{"name":"Acme Store","account":"WALLET-2002"},"reference":"INV-1001"}'
```

HTTP 201 only means the API accepted the request. Look at `status` for the payment result.

## Read the result

| `status` | RTR code | Meaning |
| --- | --- | --- |
| `pending` | PDNG | Still processing |
| `accepted` | ACSP | Accepted, settlement in progress |
| `completed` | ACSC | Settled. Payee should have the funds |
| `rejected` | RJCT | Rejected. No funds moved |

```http
GET /v1/payments/{id}
POST /v1/payments/{id}/status-check
```

If you do not want to poll, create with `?wait_for_result=true`.

## Other endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/v1/payments` | List payments |
| GET | `/v1/payments/{id}/rtr` | See generated ISO-style messages |
| GET | `/v1/health` | Rail heartbeat (`HBRT`) |
| GET | `/v1/balance` | Sample settlement balance |
| GET | `/v1/ready` | Process liveness, no API key |

## Sandbox test cases

- Payee account starting with `REJECT` → rejected
- Payee account starting with `PENDING` → stays pending
- Or set `"test_outcome": "success" | "rejected" | "pending"`

## What the API fills in

From the data dictionary: business message id, message id, UETR, trace id, settlement method `CLRG`, clearing system `RTR`, local instrument `RTREXCHANGE`, charge bearer `SLEV`, settlement date, and participant member IDs.
